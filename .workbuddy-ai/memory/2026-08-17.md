# 2026-08-17 (cont.) — FINAL PRODUCTION AUDIT: real bugs found + fixed

## Corrected earlier wrong hypothesis
Prior grep suggested core tables lacked RLS. Re-verified: **RLS IS enabled on all 18 tables**. Content
tables (wedding_halls, food_items, artists, bride_groom, banners, timeline_events, invitations, weddings,
plans) have `SELECT USING(true)` — world-readable BY DESIGN (public guest page). So the real gaps were in
the **anonymous write paths** + **RPC privilege** + **edge-function scoping**, not missing RLS.

## Bugs fixed (with file + fix)
1. **Cross-tenant RSVP/moment pollution** — `rsvps`/`wedding_moments` anon INSERT only checked `hall_id`
   exists, not that `wedding_id` belonged to that hall. Migration `20260818000100_security_hardening.sql`
   binds `wedding_id` to a wedding in the same `hall_id`.
2. **Billing/archiving RPC privilege escalation** — `confirm_subscription_payment`,
   `sync_subscription_notifications`, `archive_active_wedding`, `archive_all_active_weddings` were
   SECURITY DEFINER with NO caller check (any hall admin could grant subs / archive other venues). Added
   `is_super_admin()` / `auth.role()='service_role'` / `is_hall_admin(...)` guards in same migration.
3. **Subscription expiry not at 00:00 Tashkent** — was raw `_paid_at + 30d`. Now
   `date_trunc('day', _paid_at AT TIME ZONE 'Asia/Tashkent')` so periods start/end at midnight Tashkent.
4. **build-wedding-zip leak** — any hall admin could download ANY hall's ZIP. Now super-admin OR the
   wedding's own hall admin only (`supabase/functions/build-wedding-zip/index.ts`).
5. **archive-weddings ?hall= leak** — a hall admin could archive another hall's weddings. Now non-super
   callers are forced to their own hall (`supabase/functions/archive-weddings/index.ts`).
6. **ArchiveDetailPage** reads by `wedding_id` only; added `eq('hall_id', hallId)` to all child queries
   (`src/pages/ArchiveDetailPage.tsx`) — defense-in-depth + correctness.
7. **Duplicate active-wedding race** — `useActiveWedding` auto-created without a unique guard. Added
   partial unique index `weddings_one_active_per_hall` + resilient re-read on conflict
   (`useWeddings.ts`, migration).
8. **BrideGroomEditor edits wrong couple** — `useBrideGroom(hallId)` with no weddingId returned an
   arbitrary row in multi-wedding halls. Now scopes to the active wedding id
   (`src/components/halladmin/BrideGroomEditor.tsx`).
9. **Stale admin RSVP list** — `useSendRsvp` didn't invalidate. Added `qc.invalidateQueries(['rsvps', hallId])`
   (`src/hooks/useWeddingMoments.ts`).

# 2026-08-17 (cont.) — Super-admin "Add standard plans" (seed) button error

## Symptom
Clicking `t('superadmin.plans.seed')` ("Standart tariflarni qo'shish" / "Add standard plans") on the
super-admin Tariflar page threw an error.

## Root cause
- The seed button only renders when `plans.length === 0` (`useAllPlans` returns all plans). The `plans`
  table is created + seeded by migration `20260818000000_super_admin_billing.sql` (produced in the earlier
  audit) which was **never applied to the live Supabase project** → `plans` empty/missing.
- The old code did `supabase.from('plans').upsert(...)` directly from the browser, gated by the plans RLS
  `WITH CHECK (public.is_super_admin())`. When the table is missing this is "relation does not exist"; even
  when present, a client-side upsert through RLS is fragile.

## Fix applied
1. **NEW migration `20260818000200_seed_default_plans_rpc.sql`** — `public.seed_default_plans()` SECURITY
   DEFINER RPC: bypasses plans RLS, idempotent `INSERT ... ON CONFLICT (code) DO UPDATE`, authorizes the
   caller directly against `user_roles` (`role='super_admin'`) or `service_role`. Ordered AFTER the billing
   migration so `plans` exists when it runs.
2. **`src/hooks/useAdminData.ts` `useSeedDefaultPlans()`** — now calls `supabase.rpc('seed_default_plans')`;
   falls back to the client upsert only if the RPC is "does not exist" (i.e. migration not yet applied).

## Action required (deploy, not code)
The live Supabase project is missing the billing + hardening + RPC migrations. Apply them:
`supabase db push` (project linked) or `supabase migration up`. Until then the seed (and the whole
billing UI) cannot work — this is the dominant cause of the reported error. After applying, the seed
button works and plans are populated.

## Verified
- `tsc --noEmit` → 0.
- `vite build` (→ `.tmp-build2`, copied into `dist/`) → ✓ built in 9.02s.
