## Invitation builder: music upload — REAL root cause + fix (Android local-file picker)
- EARLIER "Telegram WebView 0-byte" theory was WRONG. User screenshot (debug `?debug=1`, commit 7454d46) proved the real UA is **Chrome/151 Android 10** (not Telegram: no `TelegramBot`/`TelegramAndroid`/`tgWeb`). So they ARE in real Chrome. File picker still delivered `size: 0 B`.
- REAL ROOT CAUSE: on some Android Chrome builds the `<input type=file>` picker returns a `File` whose `size` is misreported as 0 (a MediaStore `_SIZE` column quirk) even though `readAsArrayBuffer` still serves the REAL bytes. Our old premature `if (file.size === 0) reject` guard rejected valid files before they could be read → "can't upload from phone storage".
- FIX (`src/components/invitation/builder/forms/index.tsx` `onMusicPick`):
  1. Removed the up-front 0-byte reject. Now verify by reading bytes.
  2. Fast-path `audioMime && knownExt` now also requires `file.size > 0`; misreported-size files fall through to byte-read path.
  3. After `readFileBytes`, reject ONLY if `bytes.byteLength === 0` ("verified by read") with an accurate message (pick via Files/Documents or use URL).
  4. Hardened `readFileBytes`: if full read returns 0 bytes, retry via `f.slice(0, 50MB).arrayBuffer()` (content-URI provider serves real bytes on slice). Re-wrap surviving bytes into a fresh `File` with sniffed ext + correct MIME → Supabase upload gets readable bytes.
- Debug console (DebugOverlay + `?debug=1` gate) intentionally KEPT for now — user asked to keep it to watch the remaining error. Remove once Android upload confirmed working.
- QA: tsc PASS; `NODE_OPTIONS="" bun run build` PASS (InvitationBuilder-B8k2edtZ.js). Bundle verified: old "Telegram WebView delivers an empty file" GONE, "verified by read" present, `slice(` fallback present, overlay present. Committed (a0dab6c).

- KEY LESSON: never trust `File.size === 0` as "empty" on Android; the picker can misreport. Read the bytes (FileReader, with a slice fallback) and decide on actual `byteLength`.
